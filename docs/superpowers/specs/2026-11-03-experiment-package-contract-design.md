# 实验开发包与上传识别契约设计稿

状态：范围已确认，进入实现。用户选择“先给已有实验上传新版本”；首个已开放契约为 convex-lens，不包含新实验注册。延续独立 ZIP、隔离三维视图区、平台物理引擎和审核后自动展示流程。

## 目标

开发者选定实验，复制平台生成的任务提示词，在同版本模板里开发，运行一个发布命令得到 ZIP。系统按清单识别目标实验、检查兼容性，管理员审核通过后原子更新默认版本；不需要修改主站源码或重新构建主站。

保证来自可执行契约和验证，不来自提示词的自然语言本身。机器检查负责格式、兼容性、资源与运行握手，物理教学质量、素材许可和视觉效果仍需审核。

## 现状核对

| 当前实现 | 需要补齐的部分 |
| --- | --- |
| 提示词输入接受任意合法 experimentId，下载 AGENTS 仍有占位 ID | 生产投稿只能选择已开放的实验契约；未知 ID 不生成可上传承诺 |
| 文档 JSON Schema、本地 validate.mjs、服务端 Zod 三处分别定义规则 | 从同一个契约源生成，消除引擎、路径、版本规则差异 |
| 服务端主要解析 experiment.json，其余元数据只要求文件存在 | parameters、teaching、cases、asset licenses 均需结构和交叉引用校验 |
| npm run pack 只验证并打包现有 dist | 发布命令必须检查、清理旧产物、重新构建、验证再打包 |
| connected 消息到达即把视图区标为 ready | 新协议区分握手成功、首帧处理成功和运行失败 |
| 服务端已有 SHA 绑定、审批、默认指针和历史回滚 | 保留这部分，不重建第二条发布通道 |

## 推荐架构：一个契约源，四种生成产物

平台保存版本化实验契约，例如 `contracts/convex-lens/v2.json`。这里v2代表开发包契约；物理引擎本身仍可为optics contractVersion 1。其中声明：已注册 experimentId、适配器/引擎版本、协议版本、参数键与单位、只读事实、允许意图及安全约束、教学用显示范围、必测物理案例、渲染/资源规范。

同一契约生成：

1. **开发提示词**：具体实验 ID、不可修改字段、任务目标、允许编辑范围、模板版本与下载摘要、唯一发布命令、交付清单。通用代码风格提示词可另保留，但明确不代表已绑定某个可投稿实验。
2. **独立模板**：锁定的 SDK/协议类型、启动器、参数描述、示例视图、预览器与校验工具。贡献者主要修改三维视图、交互、素材与说明，避免自行重写握手。
3. **机器 Schema 与校验器**：浏览器、本地工具和服务端消费相同的语义规则。服务端仍独立执行 ZIP、权限、文件完整性与资源隔离检查，不信任客户端的“通过”标志。
4. **平台适配器检查**：证明宿主输出符合快照 Schema，参数意图范围与实际引擎/界面契约一致。显示范围与安全边界分开表达，不能把较小的滑杆范围误认为全部合法物理范围。

通用 HTML/JS 自由投稿虽灵活，却无法可靠地自动接到参数、记录和物理引擎。因此不作为当前默认入口。保留现有静态包架构，收紧契约，比另造上传后端更合适。

## 版本与固定文件格式

建议将完整规范作为新一代包格式发布：`schemaVersion: 2`；首帧/错误回执使用 `protocolVersion: 2`。物理模型没有改变时，`engine.contractVersion` 仍可为1。投稿内容自己的 `version` 与这些平台协议版本分开。

v2投稿内容版本统一为无前导零的三段稳定版本号（如1.0.0），总长不超过32字符。本地、服务端及Schema采用同一规则，不再各自接受不同的预发布格式。

清单由平台模板生成；开发者只改自己的内容版本，不能随意填写 ID、引擎或入口：

```json
{
  "schemaVersion": 2,
  "protocolVersion": 2,
  "packageType": "browser-static",
  "experimentId": "convex-lens",
  "version": "1.0.0",
  "entry": "dist/index.html",
  "renderer": "three",
  "theme": "physicsos-warm-lab-v1",
  "engine": { "id": "optics", "contractVersion": 1 },
  "parameters": "parameters.json",
  "teaching": "teaching.json",
  "referenceCases": "cases.json",
  "assetLicenses": "ASSET-LICENSES.json",
  "cover": "dist/assets/cover.jpg",
  "license": "Apache-2.0"
}
```

这是**设计稿的 v2 示例**，当前实现仍只接收 v1；不能把这个示例直接上传到当前服务。

迁移建议明确为：

- v2能力完整上线后，新投稿只接受v2，v1新上传返回`PACKAGE_UPGRADE_REQUIRED`及升级说明。
- 上线前已经进入待审队列的v1包保留，管理员可按原v1流程预览并完成审核；界面标明“旧格式”，不声称通过v2首帧检查。退回后重新投稿属于新投稿，使用v2。
- 已审核v1包、固定到v1的旧实验与历史回滚继续走原适配器，不重新解释或改写冻结文件。v2发布不删除v1加载器。

这是本方案的兼容性选择：保留已有投稿工作，同时让新交付进入统一规则。它不意味着当前服务器已经开始拒绝v1。

ZIP 根目录固定，不额外套一层目录：

```text
experiment.json
parameters.json
teaching.json
cases.json
ASSET-LICENSES.json
README.md
MODEL.md
LICENSE
src/
dist/index.html
dist/runtime/
dist/assets/
```

构建配置与锁文件随源码一起保存，按工具白名单收集。node_modules、预览器私有数据、.env、密钥和本机路径不进入发布包。ZIP文件名便于人识别，系统依据清单与服务端摘要识别，不能靠文件名猜测。

## 元数据与运行契约

- **parameters.json**：由所选契约生成。固定参数 ID、单位、读写方向、约束及显示建议；贡献者不能通过增加字段获得新参数权限。凸透镜的物高和像/光线显示状态来自平台，包内可写意图仍只包括物距、焦距、光屏位置。
- **teaching.json**：标题、步骤和模型限制均有类型、长度和数量约束；与 experimentId 对应。它描述教学内容，不获得定义主站导航或账号权限的能力。
- **cases.json**：必含契约规定的核心案例，附加案例使用相同的输入/期望结构。数值有限、单位明确，焦点无像用 null 而非 Infinity；可信平台引擎校验数据，不执行上传的测试脚本来决定物理正确性。
- **ASSET-LICENSES.json**：资源路径能在包中解析，许可证与来源字段符合固定格式。机器只能检查结构和引用，不能断言许可证真实或权利充分。
- **SDK**：提供初始化、快照处理、首帧确认、错误报告和清理入口；包不得直接访问账号、Cookie或业务数据库。平台验证来源、实例通道、版本、消息类型和频率。

新协议顺序为：握手 → 发送匹配契约的快照 → SDK确认处理首帧 → 显示“可运行”。失败或超时给出明确状态。`rendered` 回执是兼容性信号，不是物理正确性或可信作者证明，不能替代人工审核。

## 开发者的唯一发布命令

建议暴露 `npm run release`：

```text
格式/类型/行为检查
→ 清理 dist
→ 从源码重新构建
→ 校验清单、元数据、资源和契约
→ 生成 release/<experimentId>-<version>.zip
→ 输出 ZIP SHA-256 与校验报告
```

本地校验报告供开发者定位问题，服务器重新计算摘要和重跑规则。源码/产物摘要可检测意外陈旧，但不能把作者自行生成的报告当成源码与 dist 对应的安全证明。

生成给开发助手的提示词必须包含以下任务块，所有具体值由平台填入：

```text
目标实验：已选的 experimentId（不得自行新建或改名）
开发起点：版本锁定的独立模板URL及真实SHA-256
不可修改：清单契约字段、平台SDK、生成的参数/单位定义
可修改：实验视图、允许的交互、包内素材、教学说明与附加案例
验证与交付：执行 npm run release，失败先修复，交付release ZIP及真实校验报告
禁止：伪造通过结果、上传旧dist、接触账号/数据库、另建上传接口或修改主站
```

开发者填写的具体改进需求作为单独任务字段，不拼接进ID、Schema或SDK代码。提示词展示与下载文件、模板中的AGENTS必须使用同一个生成器。

## 上传识别与自动同步

上传 → 校验清单与目标契约 → 语义/资源检查 → 冻结 packageId 与 ZIP SHA-256 → 等待审核 → 隔离预览与首帧/参数检查 → SUPER_ADMIN 审核通过 → 更新该 experimentId 的默认指针。

上传页无需开发者再手工填写路由或部署地址。未知实验 ID、错误引擎、旧协议不兼容、缺资源或元数据错误均停止进入可发布状态。错误按稳定代码、包内文件名、JSON路径及修改建议返回；不泄露服务器路径或回显任意大段文件内容。

审批仍绑定冻结摘要。默认版本按服务端审批顺序更新，不用客户端时间或版本字符串决定谁覆盖谁。新打开的实验使用新默认；已经打开或保存的实验仍固定原 packageId，记录和历史可恢复，管理员可回滚。

## 如果允许全新实验

单独增加“申请新实验”的注册流程：目录ID、学段/学科、物理引擎及契约、参数和记录模型、教学案例经平台审核后，生成可用的专属模板。普通 ZIP 上传不凭一个新 experimentId 就自动创建全站实验或接入未知引擎。

## 实施与验收顺序

1. 以凸透镜收敛契约源，统一提示词/模板/Schema/两端校验，消除已发现的三套规则差异。
2. 补齐元数据语义校验和强制重新构建的发布命令，让真实开发者按复制的提示词产出唯一 ZIP。
3. 引入版本化 SDK 的首帧/错误回执和管理员预览检查；保留 v1 历史加载。
4. 在服务器 Docker 里按“下载模板 → 复制提示词的实际开发流程 → release → 上传 → 审核 → 新会话展示 → 旧记录保留 → 回滚”验证；增加未知ID、改单位、错协议、损坏元数据、陈旧dist与缺资源的拒绝样例。

当前正式部署状态沿用现有交接报告；本设计稿不表示 v2 已实现或正式站点已经切换。

## 设计检查

独立实施可行性检查提出两项待定问题：本轮是否包含新实验注册，以及v1新投稿/待审队列如何迁移。后者已按上文明确；前者由用户确认仅支持已有实验新版本。实现与测试按配套实施计划推进。
