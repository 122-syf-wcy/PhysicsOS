# PhysicsOS 安卓学生端：完整产品与高性能架构方案

日期：2026-11-10。

状态：用户已批准按本方案并行编码，实施与接口分工见[实现约定](../plans/2026-11-10-android-implementation.md)。服务器空间不足，用户已选择只继续编码、不扩大清理；构建、端到端和安卓真机性能尚未验证，不能据源码状态宣称正式交付完成。

## 1. 选型结论

采用 **Kotlin + Jetpack Compose 原生安卓主应用，配合本地独立实验渲染模块，复用现有 TypeScript 物理引擎与 PhysicsOS 服务端**。

应用导航、账户、课程与资料目录、题目列表、学习记录、作业、相机、文件、通知和系统生命周期由原生层负责。实验运行、交互画布及复杂数学文档使用受控的本地 WebView 渲染模块，不加载整个在线网站。

不使用整站套壳，不把现有桌面 Harness 客户端搬入手机，不在手机运行 Node 侧车，也不复制一套 Kotlin 物理算法。

此前推荐 React Native/Expo 是在兼顾跨平台与开发复用时的选择。现在目标明确为 Android 学生端、完整交付、性能与长期体验优先，原生 Kotlin 是本方案的推荐选型。React Native 并非必然不流畅；这里选择原生，是为了避免在独立 Web 实验运行时之外，再维护 React Native 的运行时和平台适配层，并直接控制安卓生命周期、后台工作、内存及系统交互。更换外层框架并不能自动解决实验内部的计算和渲染瓶颈。

代价：原生界面开发量更大；日后若开发 iOS，原生界面不能直接复用，但服务端、协议、物理引擎和本地 Web 渲染模块可继续复用。

## 2. 已确认的现有基础与约束

以下是本地源码检查结论，不代表当前线上镜像，也不代表移动端已实现：

- [物理运行时](../../../packages/physics-runtime/src/index.ts#L12)及多个引擎、题目处理模块有纯 TypeScript 共享基础；不能把所有包入口都视为浏览器可用，部分试卷模块依赖 Node。
- [实验运行更新](../../../overlays/harness/files/packages/client/ui-physicsos/src/client/PhysicsWorkspace.tsx#L241)目前由浏览器动画回调推进；[实验主画面](../../../overlays/harness/files/packages/client/ui-physicsos/src/client/physics/PhysicsCanvas.tsx#L147)使用 React/SVG，存在 DOM 测量和触摸事件依赖。已有外壳节流，但[画布帧订阅](../../../overlays/harness/files/packages/client/ui-physicsos/src/client/physics/frame-source.ts#L50-L60)仍在帧变化时触发画布 React 渲染；这是一条需要专项测量与改造的高频路径，不等于已经测得它是唯一瓶颈。
- [现有网页启动](../../../vendor/deepseek-harness/apps/web/vite.config.ts#L11)依赖宿主注入启动信息与插件资源，不能把现有静态构建目录直接作为独立 App 使用。
- [认证写入校验](../../../overlays/harness/files/packages/physicsos/auth-host/src/routes.ts#L97)依赖同源请求。移动端需要自己的原生通信适配，不能通过全面放开 CORS 或关闭 CSRF 来解决。
- 现有服务端包含账户、学习记录、班级、试卷等业务入口；聊天使用 HTTP RPC 与 WebSocket，而非假定存在一个通用 SSE 聊天接口。
- [出卷阶段接力](../../../overlays/harness/files/packages/client/ui-physicsos/src/client/PaperWorkspace.tsx#L807)仍由客户端轮询驱动。已有任务记录持久化不等于手机挂起后整个流程自动完成。

## 3. 完整功能范围

交付目标是学生权限内的完整功能，不以 Demo、MVP 或只完成少量实验替代。实施前从届时的实际产品生成逐项功能台账；台账覆盖所有学生可达入口、实验类型、状态和数据操作，不能只按页面数量统计完成度。

### 学习与解题

- 文本、拍照、相册和文档输入；裁剪、压缩、上传进度、失败重试及重复提交防护。
- 多轮解题、流式内容、公式和图形、引用、取消、重试、历史恢复及题目与实验联动。
- 保留学习过程、答案、验证结果和原始题目，不能仅保存截图。
- 会话目录、输入区和附件操作原生化。复杂数学内容使用独立的本地文档渲染器；不能每条消息创建一个 WebView。
- 完成的内容块缓存排版；流式新增内容按短时间窗合并更新，不在每个 token 到达时重排全部公式与历史内容。提供选择、复制、字号和无障碍语义。

### 实验室

- 覆盖完整实验目录与全部已支持实验类型，而不是固定几个演示模板。
- 播放、暂停、复位、单步、时间轴、参数调整、读数、曲线、验证、自测与报告。
- 自由搭建、器材选择、触控接线、拖动、缩放、撤销重做和场景保存，不因手机屏幕小直接删掉编辑能力。
- 竖屏使用画布加抽屉式参数/结果区域；横屏和平板增加并排面板。
- 所有依赖悬停的操作提供点击、长按或固定读数等触控等价入口；保留可访问的文本结果，不只展示动画。

### 题目、资料、课堂与记录

- 题目和资料的检索、筛选、浏览与已有学习入口；历史记录、收藏/保存能力与跨端恢复。
- 学生权限内的班级、作业、提交、查看反馈及试卷作答/结果流程，以现有权限为准。
- 学生能访问的试卷功能不得因其页面名称含“出卷”就被遗漏；教师编辑、学校管理和平台管理不得向学生开放。
- 支持 PDF 查看、下载和系统分享；外部内容遵守来源授权，外链不伪装为已支持离线的本地资源。

### 账户与正式产品能力

- 已有登录、注册/加入学校流程、二次验证、密码恢复、登录过期和撤销。
- 权限说明、通知设置、反馈、隐私、个人数据与账号注销流程。
- 弱网、断网、空数据、加载失败、权限拒绝、存储不足、后台恢复和新旧版本兼容都有明确行为。
- 上架前按发布地区及学生年龄范围完成隐私、未成年人保护、SDK 信息披露和适用的备案要求。

## 4. 原生主应用架构

采用单向状态流：界面消费 ViewModel 暴露的状态，数据操作进入业务用例与 Repository。使用 Kotlin Coroutines/Flow 分离 UI、网络、磁盘和计算任务，不在主线程执行大 JSON 解析、图片解码或文件处理。

本地结构化记录和待同步操作使用 Room；轻量设置使用 DataStore。原生 HTTP/WebSocket 通信集中管理，账户身份、重试、取消、幂等和错误映射不散落到各页面。

列表使用稳定标识和按需加载，图片按显示尺寸解码并设置缓存上限。高频滚动、动画和进度更新只影响必要的布局或绘制区域，不触发整个页面重新组合。

复杂公式和实验是独立受控渲染区域，而不是页面通用实现方式。禁止以大量 WebView 列表项替代原生长列表；跨实验、解题页切换时执行明确的渲染器持有、释放和恢复策略。

软件版本在实施时选择彼此兼容的稳定版本并锁定，不使用“永远取 latest”的构建配置。Android 10/API 29 及以上作为默认支持范围，4 GB 内存的入门/中端真机作为基本性能验收档；如实际学生设备需要更低系统版本，必须先验证安全 WebView 供应与性能，不只下调一个 SDK 数字。

## 5. 实验性能架构

### 5.1 独立构建与本地资源

从现有产品抽离必要的实验入口、渲染器、运行时和器材资源。移除对宿主插件图、在线会话布局、动态插件加载及根相对业务 API 的依赖。

使用 AndroidX WebKit 的 WebViewAssetLoader，以应用专属 HTTPS origin 加载随 APK 打包的 JS、CSS、字体和图片，不使用生产站域名伪装同源，也不使用 file:// 权限放宽。基础实验资源随应用发布；大型可选资源可以版本化下载并校验完整性。

可执行代码随签名 App 更新，不允许用户实验包或远程页面获得任意原生执行能力。学生自建场景优先采用经过校验的声明式数据。

### 5.2 计算与渲染解耦

权威仿真状态由独立 Worker 持有。将纯 TypeScript 引擎与执行控制抽离到 Worker；包含函数、闭包或 UI 句柄的现有运行时对象不能直接跨线程传递，应定义明确的命令、场景和结果消息。

物理步长与数值容差遵从引擎，不由屏幕帧率控制。显示可以插值和减少中间刷新，但碰撞、接线变化及其他不连续事件必须保留正确顺序，验证与读数使用权威数值。不得以改变物理精度换取流畅。

Worker 向 Web 渲染线程传递有界的最新状态及必要事件，不发送完整历史。高频数值缓冲在适用时使用可转移 ArrayBuffer，避免大对象频繁序列化；“只保留最新快照”不得丢弃必须处理的事件。计算是否迁出主线程及传输成本要分别测量，不能把加 Worker 当作自动加速。

### 5.3 绘制策略

- React 负责场景结构和低频 UI 状态；逐帧位置、轨迹等走专用绘制循环，不把每帧整场景放入 React 状态触发协调。
- SVG 保留器材结构、标签和交互命中等优势；密集轨迹、粒子和曲线采用 Canvas 2D 绘制层，并限制历史点数与可见采样量。
- 显示采样与权威结果分开；降低曲线显示密度不改变保存的数据和验证结论。
- 高频拖动、接线、平移和缩放留在 Web 渲染模块内部，不让每一次 pointer move 经 Kotlin 往返。
- 不为“高性能”预先引入复杂 WebGL、OffscreenCanvas 或 Rust/WASM 重写；如跟踪确认具体热点，再在同一结果契约与正确性测试约束下优化该热点，不削减功能交付。

### 5.4 原生桥接与生命周期

原生层只发送加载场景、保存、分享、主题和前后台等粗粒度命令，接收任务状态、检查点及必要摘要。不得在原生桥上逐帧传递完整场景、图片或曲线。

桥接消息版本化，校验类型、大小、字段和授权。仅向本地可信 origin 的主框架开放；外部网页不复用带权限的实验 WebView，禁止通配 origin 和任意原生方法调用。

同时仅保持一个活动实验渲染器与对应仿真执行器。不在首页同步初始化 WebView 阻塞首屏；预热必须有内存上限，也不能将预热结果伪装成冷启动指标。

切后台暂停绘制和本地交互仿真并保存可恢复检查点；回前台不追算离开期间全部墙钟时间。进程回收或 WebView 渲染进程退出后从状态恢复，不能依赖 WebView 对象永久存活。

## 6. 移动端服务接口与安全

沿用现有账户、权限和业务服务，增加稳定的移动 API 适配层，不重建一套数据库或绕过现有身份校验。公开接口收敛到学生业务能力，不暴露整个 Harness 管理、工具及文件系统调用面。

原生应用使用面向第一方移动端的短期访问凭证及可轮换、可撤销的刷新凭证，接入现有登录/二次验证与用户权限。不要把个人 API Token 自动当成移动登录方案。刷新凭证使用 Android Keystore 保护的密钥加密保存；Keystore 不直接存放任意令牌字符串。WebView 不持有刷新凭证、上游模型密钥或广泛可用的访问凭证。

HTTP 与 WebSocket 使用一致的身份和权限。原生网络层负责认证，不让本地 WebView 直接承担跨源登录。网页原有 Cookie/CSRF 防护保留。

移动 API 明确版本、错误类型、分页、任务状态、幂等键及支持的客户端版本区间。TS 与 Kotlin 数据类型由统一的机器可校验定义约束；服务端对请求仍执行运行时验证，不能只依赖客户端类型。

聊天事件保留顺序游标、快照和缺口恢复；重连必须补齐状态，重复事件可去重，不能只重新建立一个连接就宣称恢复完成。模型耗时与客户端响应性能分开统计。

## 7. 后台、同步与离线

试卷、解析和其他长任务的阶段接力由服务器负责，持久化任务状态，并区分可自动重试和需要用户确认的付费/非幂等操作。服务器重启后的恢复规则、取消、超时及重试必须明确，不自动重复计费。

移动端提交任务后可以锁屏或被系统回收；服务器继续处理，App 回到前台根据任务 ID 与游标补齐。Android 后台调度用于可延后同步和适用的文件任务，不承诺后台持续 WebSocket，也不使用常驻前台服务保活聊天。

推送只提示有新结果，不作为唯一数据来源。按目标国内设备接入适用的厂商推送，不能只依赖 FCM；用户拒绝通知、系统限制后台或无推送支持时，进入应用仍能同步结果。

本地数据库按账户隔离；学习记录和提交进入持久待同步队列，服务端按幂等键处理。区分服务器已确认状态、本地待提交状态及冲突，不用盲目“最后写入覆盖”解决答案、作业或场景冲突。

离线能力覆盖已下载资料、已有结果和资源齐备的本地实验；服务器解题、出卷和账户同步需要网络。退出、换账号、清理缓存和删除账号时执行对应的数据与凭据清理。

## 8. 可验收的性能门槛

以下是开发目标与初始性能预算，不是已达成的测量结果。正式开工时固定具体设备型号、系统、WebView 版本、数据集和脚本，至少包含 4 GB 入门/中端手机、常见中端手机及平板；不能只用旗舰机或模拟器给出流畅结论。

- 原生常用页面：60 Hz 基准下保持 60 fps，固定滚动/转场脚本中错过帧截止期的比例目标不超过 1%。高刷新率设备另外验收，不把实验必须跑到 120 fps 作为耗电代价。
- 实验：固定代表性及高负载场景持续运行，60 Hz 下目标 60 fps、错过帧截止期比例不超过 3%；统计 p95/p99 与最长卡顿，不只报平均帧率。所有合法场景都需功能正确，性能测试不得只选最简单模板。
- 本地点击到可见反馈：p95 不超过 100 ms；参数拖动及接线单独记录输入到呈现的延迟。
- 冷启动到可操作的本地首页：p95 不超过 2 秒；不等待网络返回或 WebView 完成初始化。首次安装初始化、认证状态恢复和完全无缓存情况分别报告。
- 本地实验首次进入到可操作：p95 目标不超过 2 秒；已加载实验恢复目标不超过 500 ms，两者分别统计。
- 初始内存预算：未初始化 WebView 的普通页面总 PSS 目标不超过 200 MiB；单实验包含渲染子进程的合计 PSS 目标不超过 400 MiB。大型文档导入单列峰值预算和降采样策略，不以 Java heap 代替全进程内存。
- 连续使用：30 分钟实验与重复页面切换，不能出现随次数持续增长的保留内存；同时记录热降频、帧率、崩溃和耗电，不用峰值冷机跑分代替长时间体验。

原生使用接近正式配置、非 debuggable 的可分析构建，配合 Macrobenchmark、Baseline Profiles 和 Perfetto。Web 模块另外记录 Worker 计算、消息传输、DOM/Canvas 绘制、长任务与输入延迟；原生帧率正常不能证明 WebView 里的实验没有停顿。

基准测试必须使用真实设备。模拟器承担功能回归，不作为发布性能证明。目标未达标时继续优化热点、缓存和绘制，不通过移除功能或降低物理正确性来通过验收。

## 9. 实施顺序与完成定义

以下是完整工程的内部顺序，不代表分期交付精简产品：

1. 锁定功能台账、学生权限、数值正确性样本和性能设备矩阵；核对源码与当前服务端能力。
2. 建立正式安卓工程、设计系统、数据层和基准测试；同步定义移动接口和本地渲染消息。
3. 抽离独立实验模块，完成 Worker、移动交互、正确性对照和性能跟踪。代表性场景是工程验证手段，不是最终功能范围。
4. 完成全部学生业务页面与原生能力，迁移长任务编排，贯通离线、同步、通知、文件及身份恢复。
5. 对所有实验类型和业务状态进行覆盖验收，再做设备性能、长时间运行、安全、无障碍及发布渠道检查。
6. 交付签名 APK、需要的渠道包、源代码与构建流程、功能验收清单、性能报告和回滚说明。

只有功能台账全部验收、真实设备性能门槛有报告支撑、后台/离线恢复通过、无占位页面或模拟接口，才算正式版本完成。不得将可安装 APK 等同于完整交付。

## 10. 构建与发布约束

用户于 2026-11-10 确认 Windows 负责安卓开发，允许 Windows 原生 JDK/SDK/Gradle 构建、模拟器与真机调试，独立实验 bundle 可在该工作站用 Node 构建。Mac 负责网页和服务端源码；网页/服务端正式构建、测试与部署仍以服务器 `107.151.246.59` 的 `/opt/physicsos` 与 Docker 为准。服务器安卓工具链保留为可选 CI 方式，不为后端部署在 Mac 补装环境。

物理设备验收需要连接到受控设备执行器或适用的真机服务；普通 Linux 容器不能提供可信的真机性能。是否使用外部真机服务、上传构建产物或发布商店，届时单独取得授权。

签名私钥与服务密钥从既有受保护文件或容器挂载获取，不进入仓库、聊天或日志。发布前核对远端 main、服务器检出版本及运行镜像，保留已上线后续修复、旧镜像和数据恢复点；数据库变更保证旧客户端与回滚路径可控。
